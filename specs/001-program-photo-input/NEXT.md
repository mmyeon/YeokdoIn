## 1. 오인식 검출 확대 (문서 먼저)

2026-09-11 실제 아이폰 사진앱 인식 결과를 넣어보니 **6줄 전체에서 검출 0건**이었다.

```text
Militery Press 5x3
Power Snatch & Squat Snatch 65% (1+1)x1,20%(2+1)x2, 25% (1+1)x 2, Squat snatch Bor. 2xd, Bfr 1xz.
Powet clean & Squat dean
65% (1+1)x2, %x. (211)x2, 25% (1+1) x2.
Squnt clean Box.2xs, Bsx 1xs.
Bade squat 7o%.
```

### N2. 의심 문자 후보를 `O l I` → 임의 문자로 확대

현재 규칙이 후보를 세 글자로 한정해 `7o%`(소문자 o), `2xd`, `1xz`, `2xs`, `1xs` 를 전부 놓친다.
문서 4장의 원칙(「숫자 자리에 문자가 오면 오인식」)은 그대로 맞고, **후보를 좁힌 것이 틀렸다.**

- `x`/`×` 뒤와 `%` 앞은 숫자만 오므로 **아무 문자나** 의심해도 오탐이 없다
- 문서 4.2 를 먼저 고치고 `suspect-spans.ts` 를 따라가게 한다
- SC-005 골든 케이스로 오탐 0건을 재확인할 것

### N3. `/` ← `%` 패턴 기록 + 검출

`Front Squat 15/3x3,80/3x3` 처럼 `%` 가 `/` 로 자주 읽힌다. 6판 원문에 `/` 가 한 번도
나오지 않으므로 「숫자 뒤 `/`」는 오탐 위험이 낮다.

- `docs/gym-program-notation.md` 4.1 에 사례, 4.2 에 규칙 추가 → 그다음 코드

### N4. 못 잡는 것 (기록만, 구현 대상 아님)

- `Bor.`, `Bfr`, `Box.`, `Bsx` ← `80%`/`85%` — 숫자가 아예 없어 판정 근거가 없다
- `20%`←`70%`, `25%`←`75%` — 결과가 유효한 숫자라 **원리적으로 탐지 불가**
- `Militery`, `Powet`, `dean`, `Squnt`, `Bade` — 종목명 오타. 어휘 대조가 있어야 가능하다
- `(211)` ← `(2+1)` — `+` 가 `1` 로 읽힘. 숫자만 남아 정상으로 보인다
- 줄바꿈 유실 (3·4번 줄이 원래 한 줄)

## 2. 편집 부담 줄이기 (새 FR 필요 — 별도 이슈)

현재 스펙에 대응 FR 이 없다. spec.md 에 FR 을 먼저 추가해야 한다.

### N5. 원탭 치환 칩 (우선순위 높음)

의심 구간을 탭하면 후보 문자가 칩으로 뜨고 한 번 더 탭하면 교체.
`l→1`, `I→1`, `O→0`, `o→0`, `/→%`, `.→,`, `z→2`, `s→5`.

지금은 4동작(항목 탭 → 캐럿 이동 → 백스페이스 → 입력)이 2탭이 된다.
모바일에서 캐럿 옮기는 비용이 가장 크다. **자동 수정이 아니라 사용자가 고르는 것이므로
FR-014(자동 수정 금지)와 충돌하지 않는다.**

### N6. 같은 패턴 일괄 치환

오인식은 사진 한 장 안에서 체계적으로 반복된다. `/` 가 12군데면 12번 고쳐야 한다.
「`/` 12건을 전부 `%` 로」 버튼 하나. `/` 처럼 규칙적인 것에서 효과가 크다.

### N7. 보조 툴바 (우선순위 낮음)

편집 중 텍스트 필드 위에 `0-9 % x ( ) + , ~` 한 줄. 캐럿 자리에 삽입.
`inputMode="numeric"` 은 **쓸 수 없다** — 한 항목에 영문 종목명이 섞여 있다.

### N8. 「다음 의심 구간으로」 순회

20줄에서 3건을 눈으로 찾는 비용이 고치는 비용보다 크다.
