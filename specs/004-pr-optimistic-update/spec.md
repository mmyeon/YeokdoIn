# PR 기록 낙관적 반영 (PR Optimistic Update)

**Created**: 2026-09-22 · **Status**: Draft · **선행 명세**: `specs/001-pr-management/spec.md`

## 요약

지금은 PR 기록을 추가·수정·삭제하면 서버 응답을 기다린 뒤 **토스트가 먼저 뜨고, 그다음에**
목록·현재 PR·추이 그래프가 바뀐다. 저장 버튼을 누른 순간 화면이 바로 바뀌게 한다. 실패하면
되돌리고 알린다.

## 만드는 것

- **FR-001**: PR 상세 화면에서 기록을 추가·수정·삭제하면 서버 응답을 기다리지 않고 기록 목록에
  바로 반영한다. 입력 폼도 그 시점에 닫힌다.
- **FR-002**: 같은 순간 **현재 PR 숫자와 추이 그래프**도 함께 바뀐다. 목록만 바뀌고 헤더 숫자가
  늦게 따라오면 지금 문제의 반쪽만 고친 것이다. 현재 PR은 서버와 같은 규칙(남은 기록 중 최대 무게)으로
  계산하고, 기록이 0건이 되면 서버처럼 현재 PR이 없는 상태가 된다.
- **FR-003**: 서버 응답이 오면 화면을 서버의 값으로 맞춘다. 화면에 먼저 그린 값은 예측일 뿐이고
  기준은 서버다.
- **FR-004**: 저장에 실패하면 화면을 **그 조작 직전 상태로 되돌리고** 실패 토스트를 띄운다.
  추가·수정 실패 시에는 입력 폼을 다시 열고 사용자가 입력한 값을 그대로 채워 둔다 — 다시 타이핑하게
  하면 안 된다. (001 FR-011 "실패 시 기존 값을 변경하지 않는다"는 이 되돌림으로 충족한다)
- **FR-005**: 상세 화면의 추가·수정·삭제는 **성공 토스트를 띄우지 않는다.** 화면이 바뀐 것이 곧
  피드백이고, 토스트는 실패할 때만 뜬다.
- **FR-006**: PR 목록 화면의 신규 등록(미등록 종목 → PR 등록 대화상자)은 **범위 밖**이다. 지금처럼
  저장이 끝난 뒤 대화상자가 닫히고 성공 토스트가 뜬다. 근거는 결정 기록.
- **FR-007**: 오프라인이면 지금처럼 **대기열에 쌓지 않고 즉시 실패**시킨다(`FAIL_FAST_WHEN_OFFLINE`
  주석 참조). 낙관적 반영과 합쳐지면 화면이 잠깐 바뀌었다가 곧 되돌아가고 실패 토스트가 뜬다.

## 경계

- **연속 조작**: 기록 두 개를 빠르게 삭제하다 두 번째만 실패하면 두 번째만 되돌아온다. 첫 번째
  삭제까지 되살아나면 안 된다. 진행 중인 조작이 끝나기 전 도착한 오래된 서버 응답이 최신 예측을
  덮어써서 화면이 깜빡이면 안 된다.
- **현재 PR 기록을 삭제**: 최대 무게 기록을 지우면 헤더는 즉시 다음으로 큰 무게로 내려간다.
- **동일 최대 무게가 여럿**: 헤더의 무게는 같으므로 어느 행이 선택됐는지는 화면에 영향이 없다.
  달성 날짜가 달라질 수 있으나 서버 응답(FR-003)이 바로잡는다.
- **새 기록의 정렬 위치**: 추가한 기록은 목록의 최종 위치(날짜 내림차순)에 바로 들어간다. 맨 위에
  붙였다가 서버 응답 후 자리를 옮기면 그 점프가 새 깜빡임이 된다.
- **입력 검증 실패**(0 이하, 소수, 미래 날짜): 화면 반영 전에 막는다. 서버에 보내 봐야 거부될 값을
  먼저 그렸다가 되돌리지 않는다.

## 검증

- 네트워크를 느리게(예: 3초 지연) 걸어도 저장 버튼을 누른 즉시 목록·현재 PR·그래프가 모두 바뀐다.
- 저장을 강제로 실패시키면 세 곳 모두 직전 값으로 돌아가고, 추가·수정은 폼이 입력값을 보존한 채 다시 열린다.
- 오프라인에서 저장하면 버튼이 '저장중'에 멈추지 않는다(기존 `usePersonalRecords.offline.test.tsx` 유지).
- 연속 삭제 중 하나만 실패시킨 경우 나머지 삭제는 유지된다.

## 가정

- 한 사용자가 한 기기에서 조작한다. 다른 기기에서 동시에 같은 종목을 고치는 충돌은 다루지 않는다.
- 레거시 `useAddPersonalRecord` / `useDeletePersonalRecord` 는 이 기능의 대상이 아니다.

## 결정 기록

| 안 한 것 | 이유 | 재검토 트리거 |
|---|---|---|
| 오프라인 저장 대기열 | 001에서 기각. 저장됐다고 착각하고 자리를 뜨는 편이 더 나쁘다. 낙관적 반영이 이 착각을 더 키우므로 더더욱 안 한다 | 체육관 오프라인 기록이 실제 요구로 드러나면 |
| 서버 확인 후 성공 토스트 | 화면이 먼저 바뀌고 1~2초 뒤 토스트가 따라오면 신호가 두 번 온다. "토스트 = 실패"로 의미를 하나로 둔다 | 성공했는지 헷갈린다는 실사용 피드백이 나오면 |
| 삭제 되돌리기(undo) 토스트 | 되돌리기 동작을 새로 만들어야 해 범위가 커진다. 삭제는 이미 확인창을 거친다 | 실수 삭제가 실제로 발생하면 |
| 목록 화면 신규 등록의 낙관적 반영 | 서버가 PR 행을 새로 만들어서 낙관적 행의 id는 임시값이다. 확정 전에 누르면 상세 화면이 "기록을 찾을 수 없습니다"를 보여준다. 불편이 보고된 곳은 상세 화면이고, 첫 등록은 드물어 기다려도 된다 | 첫 등록 대기가 실제로 불편하면 |
| 서버 응답 후 재조회 없이 예측값 확정 | 현재 PR·이전 무게(`previous_weight`)는 서버가 재계산한다. 클라이언트 예측만 믿으면 드리프트가 쌓인다 | — |
