# Phase 0: Research — 운동 잔디 그리드

명세의 NEEDS CLARIFICATION 은 0건이었다. 여기 남긴 것은 **계획을 세우며 갈렸고, 다시 알아내는
데 비용이 드는 판단**만이다. 조사 과정은 버리고 결론만 남긴다.

## R1. 데이터 접근: 전용 쿼리를 만들지 않는다

**결정**: 신규 api 레이어 없음. 기존 `usePrograms()`(→ `features/programs/api/programs.ts`
의 `listPrograms`)가 반환하는 `ProgramRow[]` 의 `created_at` 을 그대로 쓴다.

**근거**: `app/page.tsx` 는 **이미** `usePrograms()` 를 호출해 전체 `programs` 를 받고 있다.
그리드는 같은 화면에 있고 `created_at` 하나만 더 필요하다. 전용 쿼리를 추가하면 같은 행을 한
화면에서 두 번 받게 되고, React Query 키가 갈라져 프로그램을 저장했을 때 한쪽만 갱신되는
무효화 버그의 자리가 생긴다.

**기각한 대안**:
- `created_at` 만 뽑는 전용 서버 액션 — 위 이유. 규모도 근거가 없다(spec 가정: 6개월 수백 건).
- 날짜별 집계를 SQL 로 — `date_trunc` 는 서버 타임존에서 자른다. FR-002 가 요구하는 경계는
  **사용자 로컬 자정**이고 서버는 그 값을 모른다(R2).

**재검토 트리거**: `programs` 행이 커져(`source_text` 누적) 홈 초기 로드가 체감상 느려지면,
그때 `created_at` 전용 경량 쿼리를 만든다.

## R2. 날짜 버킷팅: 클라이언트에서, 타임존을 주입받아

**결정**: `localDateKey(isoInstant, timeZone)` 순수 함수가
`Intl.DateTimeFormat('en-CA', { timeZone, year:'numeric', month:'2-digit', day:'2-digit' })`
로 `YYYY-MM-DD` 를 만든다. `timeZone` 은 UI 가
`Intl.DateTimeFormat().resolvedOptions().timeZone` 으로 얻어 주입한다.

**근거**: 이 코드베이스는 같은 벽에 이미 부딪혔다 — `features/personal-records/model/
pr-date-bounds.ts` 는 "서버가 요청자의 타임존을 모른다"를 이유로 서버 판정을 UTC+14 여유로
느슨하게 두고 정확한 판정을 클라이언트에 맡긴다. 그리드는 **정확한 판정만 필요**하므로(느슨한
쪽이 의미가 없다) 판정 자체를 클라이언트에 둔다.

실측으로 확인한 것 (2026-09-17, Node 로컬 실행):

| 입력 (UTC 시각) | `Asia/Seoul` | `UTC` |
|---|---|---|
| `2026-09-16T14:50:00Z` | `2026-09-16` | `2026-09-16` |
| `2026-09-16T15:30:00Z` | `2026-09-17` | `2026-09-16` |

두 번째 행이 spec 의 "자정을 넘긴 훈련" 경계다. 서버 UTC 로 잘랐다면 칸이 하루 밀린다.

`en-CA` 를 쓰는 이유: 이 로케일이 `YYYY-MM-DD` 를 내주므로 `formatToParts` 로 조립할 필요가
없다. `toISOString().slice(0,10)` 은 **항상 UTC** 라 쓸 수 없다.

**부수 효과**: `timeZone` 이 인자라서 테스트가 프로세스 `TZ` 환경변수에 의존하지 않는다.
`testEnvironment: node` 그대로 여러 타임존을 한 파일에서 검증할 수 있다.

## R3. 주 시작 요일: 월요일

**결정**: 각 열의 첫 행은 월요일, 마지막 행은 일요일. 명세가 정하지 않은 값이라 여기서 정한다.

**근거**: 사용자가 한국에 있고 ISO-8601 주 정의가 월요일 시작이다. 더 중요한 건 훈련 맥락 —
주간 프로그램은 월요일에 시작하고 주말이 회복일인 경우가 많아, 일요일 시작이면 한 주의 훈련이
두 열에 걸쳐 잘린다.

**기각한 대안**: 일요일 시작(깃허브 관례) — 잔디의 시각적 관례일 뿐 이 앱의 주 단위와 맞지 않는다.

**따라오는 것**: "오늘 포함 최근 26주"(FR-005)는 **오늘이 속한 주의 월요일**을 마지막 열의
시작으로 잡고 거기서 25주를 되짚는다. 그래서 첫 열과 마지막 열 모두 잘릴 수 있다(spec 경계의
"잘린 주") — 마지막 열의 미래 요일은 `n/a`, 첫 열의 창 밖 요일은 셀 없음이다.

## R4. 폭과 터치 타깃: 계산된 충돌

**결정**: 그리드를 `repeat(26, minmax(0, 1fr))` + `gap: 2px` + 셀 `aspect-square` 로 만든다.
폭이 컨테이너에서 나오므로 **가로 스크롤이 구조적으로 불가능**하다(FR-006 을 CSS 가 보장).

**실측** (375px 기준, 2026-09-17 계산):

```
375(뷰포트) − 32(홈 px-4) − 24(카드 내부 p-3) − 14(요일 라벨 열) − 2(라벨 gap) = 303px
(303 − 25 × 2px gap) ÷ 26 = 9.73px/셀
```

spec 결정 기록이 말한 "26주면 10px" 와 일치한다. 고정 px 로 박지 않고 `1fr` 로 두는 이유는
라벨 폭이나 카드 패딩을 나중에 손대도 스크롤이 생기지 않게 하기 위해서다.

**확인한 제약**: WCAG 2.2 의 Target Size (Minimum, 2.5.8) 는 24×24 CSS px 를 요구하고,
간격 예외는 각 타깃 중심의 24px 원이 겹치지 않을 때만 성립한다. 피치가 11.7px 이므로 겹친다 —
**이 기능은 그 기준을 만족할 수 없다**. 명세의 두 요구가 물리적으로 충돌한다.
완화책과 그 근거는 plan.md 의 Complexity Tracking 에 기록했다.

**색 비의존**(FR-010): 켜짐은 채움 + 꺼짐은 테두리만으로 구분해 **채움 여부**가 신호가 되게
한다. 색상 차이가 사라져도(흑백·색각 이상) 명도 대비로 남는다. 각 셀 `<button>` 에는
`aria-label` 로 날짜와 활동 여부를 문자로 싣는다.

## R5. 상세 표시: 인라인, 신규 의존성 없음

**결정**: 선택한 날의 요약을 그리드 **바깥의 고정 자리**에 렌더한다(`GridDayDetail`).
Popover/Dialog 를 쓰지 않는다.

**근거**: FR-008 이 "이 표시는 홈의 다른 조작을 막지 않는다"고 못 박았다. Dialog 는 정의상
이를 위반하고, Popover 는 `@radix-ui/react-popover` 신규 설치가 필요한데(`components/ui/` 에
없음) 10px 셀 위에 앵커된 팝오버는 화면 가장자리 열에서 위치 보정이 계속 문제가 된다.
고정 자리는 의존성 0, 위치 계산 0, 레이아웃 점프 0이다.

**따라오는 것**: 선택 전에도 자리를 차지해야 레이아웃이 튀지 않는다. 선택 전 기본 표시는
오늘 날짜의 요약으로 둔다 — 빈 자리를 만들지 않으면서 FR-007 의 "오늘 구별"과도 맞는다.
